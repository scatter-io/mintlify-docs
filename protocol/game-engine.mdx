Scatter's games run entirely on-chain. Every player action is a signed transaction, every outcome is determined by verifiable on-chain randomness, and every bet is settled by audited smart contracts on Solana. There is no off-chain server picking results.

### Where games run

Game logic executes inside a [MagicBlock Ephemeral Rollup](/protocol/risks/rollup-risk), a high-performance execution layer that inherits Solana's security while delivering the low latency required for real-time play. Bets are submitted from the player's embedded wallet, processed in the rollup, and settled to Solana mainnet.

This gives games fast response times without giving up the transparency or composability of running on a public chain.

### Regional rollups

To minimize latency, Scatter operates Ephemeral Rollup instances in multiple regions and routes each player to the closest one. A bet placed from Tokyo settles in the Asia rollup; a bet placed from London settles in the EU rollup.

Each regional rollup is an independent execution environment, but every rollup commits its final state back to the same Solana mainnet. Balances, bet history, and wallet state are therefore globally consistent regardless of which region a bet was placed in.

Scatter currently runs rollups in:

* AS (Asia)
* EU (Europe)
* NA (North America)

Routing happens automatically based on connection geography. No setup is required.

Players are able to override the automatically selected rollup in their settings page for a more consistent experience.

### Randomness

Every random outcome is generated by an on-chain [VRF](/protocol/provable-fairness/verifiable-randomness) (Verifiable Random Function). A VRF returns a random value alongside a cryptographic proof that anyone can verify, so the result cannot be influenced by Scatter, the player, or any third party.

The VRF inputs and proofs for every bet are stored on-chain alongside the bet itself.

### Commit-reveal for hidden-state games

Some game formats need hidden state during play. In blackjack the dealer's hole card is concealed until the player acts. In mines the bomb positions are fixed at the start of the round but only revealed as the player picks tiles.

Scatter solves this on a public chain using a commit-reveal scheme:

1. Commit: Before play starts, the game publishes a cryptographic hash of all hidden state for the round on-chain.
2. Play: The player makes their decisions with the hidden state still concealed.
3. Reveal: At the end of the round, the underlying state is revealed on-chain. Anyone can verify the revealed state matches the original commitment.

The result is fixed at the moment the bet is placed, even though the player cannot see it during play.

### Bet flow

<Steps>
  <Step title="Sign bet">
    The player signs a bet transaction from their embedded wallet.
  </Step>
  <Step title="Route to rollup">
    The transaction is routed to the Ephemeral Rollup.
  </Step>
  <Step title="Generate randomness">
    VRF returns a random value with proof.
  </Step>
  <Step title="Resolve outcome">
    Game logic resolves the outcome on-chain.
  </Step>
  <Step title="Settle state">
    Wallet balance is updated and state settles to Solana mainnet.
  </Step>
</Steps>

Every step is visible on-chain.

### Verification

Every bet on Scatter is independently verifiable.

* The bet history page shows the seed, VRF proof, and any commitments for each bet.
* An inline [Verify button](/protocol/provable-fairness/overview) re-derives the outcome from the published inputs and confirms it matches the result you received.

### Composability

Because games run on Solana, anything else on Solana can read and react to Scatter's activity. Game state, bet outcomes, and vault data are all on-chain and queryable. The protocol is built to allow third-party builders to ship new games on top of Scatter's settlement and randomness primitives.
