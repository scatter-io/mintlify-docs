### VRF

A Verifiable Random Function maps an input to a pseudorandom output along with a cryptographic proof. Anyone holding the public key can verify that the output was correctly computed from the input, without learning the secret key. This gives three guarantees:

* Unpredictability: The output cannot be predicted without the secret key.
* Verifiability: The output can be verified by anyone after the fact.
* Binding: The output is uniquely determined by the input. The same input always produces the same output.

Scatter uses MagicBlock's [Ephemeral VRF](https://github.com/magicblock-labs/ephemeral-vrf), which implements RFC 9381 on the Curve25519 elliptic curve using the Ristretto group. Proofs use a Schnorr-like signature scheme with SHA-512 hashing. The implementation has been audited by Zenith.

#### VRF flow

1. The Scatter game program submits a randomness request through a cross-program invocation to the MagicBlock VRF program. The request is queued on-chain.
2. An oracle picks up the request and computes the random value along with the VRF proof.
3. The VRF program verifies the proof on-chain. If verification fails, the callback never executes and no randomness is delivered.
4. After successful verification, the VRF program calls back into the Scatter game program with the random value.
5. The Scatter program consumes the random value, resolves the bet, and writes the outcome on-chain.

Every step is recorded on-chain. The request, the proof, the verification, and the consumed output are all independently queryable.

### Seed commit-reveal

Every bet on Scatter is bound by a seed commit-reveal alongside the VRF. The seeds prevent any party from manipulating which VRF output is consumed for a given bet, since the outcome derivation is tied to seeds that are committed before randomness is drawn.

There are two seeds per bet:

1. Server seed: a secret committed by Scatter ahead of time. The hash of the active server seed is published before any bet uses it, so players can verify the seed was not chosen retroactively. The seed is rotated every 12 hours, and previous seeds are revealed in full so any past bet can be re-derived.
2. Client seed: a value managed by your client as a hash chain, advanced on each bet. The client seed gives you direct input into the randomness used for your bet.

The server seed, client seed, and VRF output are combined to produce the input that drives the game's outcome derivation. Because all three are committed before resolution and revealed after, no party can manipulate the result.

#### Why this prevents cheating

* The player cannot cheat: The VRF is generated by an oracle outside the player's transaction. The player cannot replay, reject, or re-roll the VRF output.
* The oracle cannot cheat: The VRF output must verify against the on-chain proof. An invalid proof causes the callback to fail and the result to be discarded.
* Scatter cannot cheat: The server seed is committed in hashed form before any bet uses it, and revealed after. Substituting a different seed after the fact would not match the prior commitment.
* A colluding player and oracle cannot cheat: The request commits to the client seed before the oracle generates the output, so the result is locked in before any party can see it.

### State commit-reveal (Blackjack only)

Some game formats need state that is hidden from the player during play but fixed at the moment the bet is placed. Blackjack is the canonical example: the dealer's hole card must stay concealed until the player has finished acting, but it must already be determined when the player makes their decisions.

For Blackjack only, Scatter uses a state commit-reveal mechanism on top of the standard VRF and seed commit-reveal:

1. Commit: Before play starts, Scatter generates a secret and publishes a SHA-256 hash of it on-chain. The hash becomes the binding commitment for the hidden state.
2. Play: The player makes their decisions with the hidden state still concealed.
3. Reveal: At the end of the round, the underlying state is revealed on-chain. Anyone can hash it and confirm it matches the original commitment. The hole card is then derived from the combination of the initial VRF entropy and the released secret.

Other games on Scatter resolve outcomes through VRF and seed commit-reveal alone. They do not need state commit-reveal because no hidden state persists across player decisions. In Mines, for example, each tile reveal triggers its own VRF call, so the mine layout is determined tile-by-tile rather than pre-committed.

See the [Blackjack page](/games/blackjack) for the full mechanism, including the insurance assertion that ties the hole card commitment to the insurance decision.
