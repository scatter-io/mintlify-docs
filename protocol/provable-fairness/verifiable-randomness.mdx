### VRF

A Verifiable Random Function maps an input to a pseudorandom output along with a cryptographic proof. Anyone holding the public key can verify that the output was correctly computed from the input, without learning the secret key. This gives three guarantees:

- Unpredictability: The output cannot be predicted without the secret key.
- Verifiability: The output can be verified by anyone after the fact.
- Binding: The output is uniquely determined by the input. The same input always produces the same output.

Scatter uses MagicBlock's [Ephemeral VRF](https://github.com/magicblock-labs/ephemeral-vrf), which implements RFC 9381 on the Curve25519 elliptic curve using the Ristretto group. Proofs use a Schnorr-like signature scheme with SHA-512 hashing. The implementation has been audited by Zenith.

#### VRF flow

1. The Scatter game program submits a randomness request through a cross-program invocation to the MagicBlock VRF program. The request is queued onchain.
2. An oracle picks up the request and computes the random value along with the VRF proof.
3. The VRF program verifies the proof on-chain. If verification fails, the callback never executes and no randomness is delivered.
4. After successful verification, the VRF program calls back into the Scatter game program with the random value.
5. The Scatter program consumes the random value, resolves the bet, and writes the outcome on-chain.

Every step is recorded onchain. The request, the proof, the verification, and the consumed output are all independently queryable.

### Server-seed authorization

Scatter combines a server seed, a client seed, and verifiable VRF randomness to determine game outcomes.

Before betting, your app receives the active server seed and a signed authorization tied to your wallet and an expiry. The game program verifies this authorization when processing the transaction.

The server seed is available before the bet resolves. Knowing the seeds alone does not reveal the future VRF output.

Blackjack additionally uses a separate secret commitment to conceal the dealer’s hole card during play.

### State commit-reveal (Blackjack only)

Some game formats need state that is hidden from the player during play but fixed at the moment the bet is placed. Blackjack is the canonical example: the dealer's hole card must stay concealed until the player has finished acting, but it must already be determined when the player makes their decisions.

For Blackjack only, Scatter uses a state commit-reveal mechanism on top of the standard VRF and server-seed authorization:

1. Commit: Before play starts, Scatter generates a secret and publishes a SHA-256 hash of it on-chain. The hash becomes the binding commitment for the hidden state.
2. Play: The player makes their decisions with the hidden state still concealed.
3. Reveal: At the end of the round, the underlying state is revealed on-chain. Anyone can hash it and confirm it matches the original commitment. The hole card is then derived from the combination of the initial VRF entropy and the released secret.

Other games on Scatter resolve outcomes through VRF and server-seed authorization. They do not need state commit-reveal because no hidden state persists across player decisions. In Mines, for example, each tile reveal triggers its own VRF call, so the mine layout is determined tile-by-tile rather than pre-committed.

See the [Blackjack page](/games/blackjack) for the full mechanism, including the insurance assertion that ties the hole card commitment to the insurance decision.
